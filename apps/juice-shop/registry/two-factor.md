## Notes

- **Techniques.** The setup form's Save is a decision table of the two fields
  (`rules/TC-TWOFACTOR-04.yaml`, five rules over eight combinations); the code field is a boundary
  of six digits (TC-TWOFACTOR-11). Partitions of the setup and the removal: right password and code,
  wrong password, wrong code (TC-TWOFACTOR-02, -03, -17, -18). The code's time window is a boundary
  of steps: -2, -1, +1, +2 (TC-TWOFACTOR-12). The state of the account (off, on, waiting for a code,
  signed in, off again) is walked by TC-TWOFACTOR-02, -07, -08, -09 and -17.
- **Data and writes.** Every case that signs in or changes the setting takes an account of its own
  (`actor('customer', { fresh: true })`): turning two-factor authentication on changes how the
  account signs in, so the worker's shared customer never takes it. Juice Shop cannot remove an
  account; it goes with the next container restart. No case is destructive.
- **Arranging the setting.** The cases whose subject is the setup form send it through the page
  (-02, -03, -06, -16, -19, -21, -25); -01, -04, -05, -22 and -26 only read the form, with the
  worker's customer, whose setting is never turned on. Every other case turns it on through `api/`
  (`GET /rest/2fa/status`, then `POST /rest/2fa/setup` with the `setupToken` and a code from the same
  answer) before what it checks: -07 and -24 for the "on" state, the removal and sign-in cases.
- **Results checked through the API.** The setup and removal cases read `GET /rest/2fa/status`, not
  only the confirmation; the login cases read `GET /rest/user/whoami` for the session.
- **Codes and time.** The code comes from the account's secret and the real clock; the server's
  clock cannot be moved, so a case never uses `page.clock` for it. A code made near the end of its
  30-second step can be checked in the next one, which turns -1 into -2 (TC-TWOFACTOR-12): the
  helper waits for a fresh step when too little of the current one is left.
- **The setup page's console error** (LOCAL-61) would fail the page health guard of every case on
  that page. Those cases allow that one message, with the key, until it is fixed; TC-TWOFACTOR-24
  is the case that keeps it visible as a known gap.
- **Without a requirement.** TC-TWOFACTOR-24, -26 and -27 cover the layout dimension: the page
  health guard and the visual cases. The visual case of the setup page masks the QR code, which
  changes with every secret.
- **Devices.** Every case runs on every device project of the environment. Neither page has a
  responsive difference beyond the account menu (`components/account-menu.ts`), and neither form
  has a link in its Tab order, so the keyboard cases need no WebKit exclusion. No case is pairwise.
